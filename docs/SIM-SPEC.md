# NetLab simulators specification (Phase 4)

NetLab is a Node/Express + PostgreSQL learning site for Thai vocational students (ปวช./ปวส.).
Students use lab PCs (Chrome/Edge, 1366×768 typical) and sometimes phones (360–414 px).
All simulators must contain **real logic** (no fake UI, no hard-coded results) and **all UI text is Thai**
(English technical terms are fine). Read the existing styles in `public/index.html` (CSS variables) before building UI.

There are 5 simulators. Each has two halves:

| simulator | browser module | server grader |
|---|---|---|
| shared network engine | `public/js/sim/netsim.js` (UMD: works in browser and Node) | — |
| Network Topology Simulator | `public/js/sim/topology.js` | `server/sims/topology.js` |
| Subnetting Simulator | `public/js/sim/subnet.js` | `server/sims/subnet.js` |
| UTP Crimping Simulator | `public/js/sim/crimp.js` | `server/sims/crimp.js` |
| Network Terminal Simulator | `public/js/sim/terminal.js` | `server/sims/terminal.js` |
| Network Troubleshooting Lab | `public/js/sim/troubleshoot.js` | `server/sims/troubleshoot.js` |

The app shell (written by the lead developer, not you) provides routing, login and saving. You only
write the files assigned to you. Do not edit any other project file.

## 1. Browser module contract

```js
'use strict';
(function () {
  const CSS = `...`; // inject once into <style id="nls-<sim>-css">; every class prefixed .nls-<sim>-
  window.NL_SIMS = window.NL_SIMS || {};
  window.NL_SIMS['topology'] = {
    title: 'จำลองการออกแบบเครือข่าย',
    mount(root, ctx) { /* build everything inside root; return { destroy() } */ }
  };
})();
```

`ctx` (provided by the app):

```js
ctx = {
  missions,        // array from the server grader's `missions` (public fields only, see §2)
  done,            // { [missionId]: { best: number, max: number, attempts: number } } (empty for guests)
  user,            // { name } or null (guest: grading still works, nothing is saved)
  newProblem(missionId) -> Promise<{ problem, token }>   // only for graders that export generate()
  submit(missionId, payload, extra) -> Promise<{ score, max, ok, feedback: string[], details?, saved }>
      // extra = { problem, token } for generated problems; rejects with Error(message) on failure
  toast(text)      // small notification
}
```

Rules for every browser module:
- Build UI only inside `root`; several sims never coexist, but do not use global ids anyway. Scope queries to root.
- Colors only through CSS variables: `--bg --panel --ink --muted --line --field --blue --green --orange --brown --wo --ok --bad`
  (light and dark themes switch these). Fonts: `inherit`; monospace `"JetBrains Mono",Consolas,monospace`.
- Must work with mouse **and** touch (use Pointer Events for drag) **and** keyboard (every action reachable by buttons/menus).
- No horizontal page overflow at 360 px. Large canvases scroll inside their own box.
- No `localStorage` except for an autosave draft of the student's current work (`nl-sim-<sim>-draft`), wrapped in try/catch.
- No `alert()/confirm()` for normal flow (use inline messages). No network calls except through `ctx`.
- Every simulator shows: a short **คำแนะนำการใช้งาน** (how to use), a **mission list** with status
  (ยังไม่ทำ / คะแนนดีที่สุด x/y), **hints** (คำใบ้, revealed on request), a **ตรวจคำตอบ / ส่งงาน** button
  that calls `ctx.submit`, and shows the returned score + feedback list. A free-play mode where it makes sense.
- `destroy()` must remove listeners/timers.

## 2. Server grader contract

```js
'use strict';
module.exports = {
  id: 'topology',
  title: 'จำลองการออกแบบเครือข่าย',
  missions: [
    { id: 't1', title: '...', level: 'easy'|'medium'|'hard', desc: 'what to do (Thai)', max: 10,
      hints: ['...'],              // sent to the browser (hints cost nothing in sims)
      start: { ... } }             // optional public starting data (e.g. a topology); NEVER answers
  ],
  // optional: problems generated by the server (signed by the app with HMAC so they cannot be forged)
  generate(missionId, rand) { return problem; },        // rand() -> float in [0,1), seeded by the app
  // required: pure function, no I/O; must never throw for bad input (return score 0 + feedback)
  grade(missionId, payload, problem) {
    return { score, max, ok: score === max, feedback: ['ข้อความภาษาไทย ...'], details: {...} };
  }
};
```

- `grade` must validate `payload` defensively (it comes from the browser). Cap sizes (e.g. ≤ 60 devices, ≤ 150 links).
- Feedback explains what is wrong and why, in Thai, at ปวช. level. Do not reveal a full answer key in feedback for
  assessed missions; pointing to the wrong field ("Default gateway ของ PC2 ไม่อยู่ในวงเดียวกับ IP") is good.
- Missions: 5–8 per simulator, increasing difficulty, tied to the course (Thai vocational networking, 18 weeks).
- Write a test file `tests/sims/<sim>.test.js` (plain Node, `assert`, no framework) that exercises `grade` with a
  correct payload (full score) and several wrong payloads. It must exit non-zero on failure.

### 3.1 Topology JSON (the single format used by all network sims, the bank and the graders)

```js
{
  devices: [
    // end hosts: pc, laptop, server, printer
    { id: 'pc1', type: 'pc', name: 'PC1', x: 120, y: 200,
      ifaces: [{ name: 'eth0', ip: '192.168.1.10', prefix: 24, mac: '00-1A-2B-00-00-01', up: true }],
      gateway: '192.168.1.1', dns: ['192.168.1.5'], dhcp: false,
      firewall: { icmp: true },                    // false = host blocks incoming ping (Windows default on Public)
      services: {                                   // servers mostly
        dns:  { records: { 'www.netlab.test': '203.0.113.80', 'srv.lab.local': '192.168.1.5' } },
        dhcp: { start: '192.168.1.100', end: '192.168.1.199', prefix: 24, gateway: '192.168.1.1', dns: ['192.168.1.5'] },
        web: true, file: true
      } },
    // laptop on Wi-Fi uses iface name 'wlan0' and a link with medium 'wifi' to an AP
    { id: 'sw1', type: 'switch', name: 'Switch1', x: 300, y: 200, ports: 24 },          // L2, learns MACs
    { id: 'ap1', type: 'ap', name: 'AP-Lab', x: 300, y: 80, ssid: 'NETLAB', security: 'WPA2', ports: 1 },  // bridges wifi <-> wired
    { id: 'r1', type: 'router', name: 'Router1', x: 500, y: 200,
      ifaces: [{ name: 'g0/0', ip: '192.168.1.1', prefix: 24, up: true }, { name: 'g0/1', ip: '10.0.0.1', prefix: 30, up: true }],
      routes: [{ net: '0.0.0.0', prefix: 0, via: '10.0.0.2' }],
      services: { dhcp: { ...same shape as above, optional } } },
    { id: 'net', type: 'internet', name: 'Internet', x: 700, y: 200,
      ifaces: [{ name: 'wan', ip: '10.0.0.2', prefix: 30, up: true }],
      hosts: { '8.8.8.8': 'dns.google', '1.1.1.1': 'one.one.one.one', '203.0.113.80': 'www.netlab.test' } }
  ],
  links: [
    { id: 'l1', a: { dev: 'pc1', port: 'eth0' }, b: { dev: 'sw1', port: 'p1' }, medium: 'utp', up: true },
    { id: 'l2', a: { dev: 'laptop1', port: 'wlan0' }, b: { dev: 'ap1', port: 'wifi' }, medium: 'wifi', up: true },
    { id: 'l3', a: { dev: 'ap1', port: 'p1' }, b: { dev: 'sw1', port: 'p2' }, medium: 'utp', up: true }
  ]
}
```

Rules:
- Switch ports are `p1..pN`; AP has wired ports `p1..pN` and one shared radio port `wifi` (many links allowed on `wifi`).
  Hosts have one interface (`eth0`, or `wlan0` for wireless). Routers have `g0/0..g0/3`. Internet has `wan`.
- `medium`: `utp` | `fiber` | `wifi`. Wi-Fi links are only valid between a host `wlan0` and an AP `wifi` port.
  A Wi-Fi client may set `ssid` on its device; if it differs from the AP's ssid the link is not associated (down).
- Each port holds at most one link (except AP `wifi`).
- `up:false` on a link = unplugged/broken cable. `up:false` on an iface = disabled adapter (`ip link set down`, disabled NIC).
- `dhcp:true` on a host: it gets an address from a DHCP service reachable in its broadcast (L2) domain
  (a server or router `services.dhcp`, assign addresses in order of device id, deterministic). If none is reachable
  the host self-assigns APIPA `169.254.x.y/16` (deterministic from the MAC) with no gateway.
- MACs: if missing, generate deterministically from device index.
- Internet device: answers ICMP for its own iface IP and for any IP in `hosts`; it routes nothing else.
  `nslookup` of public names works if the host's DNS server is `8.8.8.8`/`1.1.1.1` (reachable) or a local DNS server
  that has the record (no recursion modelling needed beyond: a local DNS server forwards unknown names to the
  internet if the server itself can reach 8.8.8.8 — keep it simple and documented).

### 3.2 API

```js
const net = NetSim.create(topo);           // deep-copies and normalises; never throws on bad data
net.topo                                    // the normalised topology (with generated MACs, port names)
net.problems()  -> [{ level: 'error'|'warn', code, msg /* Thai */, dev?, link? }]
    // codes: bad_ip, bad_prefix, ip_is_network, ip_is_broadcast, dup_ip, gw_not_in_subnet, gw_missing,
    //        no_link, port_in_use, wifi_wrong_end, ssid_mismatch, router_overlap, loop (switch loop warn),
    //        dhcp_none (APIPA), dns_missing ...
net.config(devId)  -> { ip, prefix, mask, network, broadcast, gateway, dns:[], mac, dhcp, apipa, up }   // effective (after DHCP)
net.ping(srcId, target, { count: 4 }) -> {
    ok, target, resolved /* ip or null */, reason,   // reason codes below
    replies /* 0..count */, path: [devId...],        // forward path of the first packet (for animation)
    win: [lines],  linux: [lines]                    // realistic outputs (see 3.3)
}
net.traceroute(srcId, target) -> { ok, hops: [{ ip, devId, rttMs }|{ timeout: true }], win: [lines], linux: [lines] }
net.nslookup(srcId, name) -> { ok, ip, server, lines: [lines] }
net.arp(devId)    -> [{ ip, mac, type: 'dynamic' }]         // after any pings made so far in this net instance
net.routes(devId) -> [{ net, prefix, via|null, iface }]     // hosts: connected + default; routers: connected + static
net.macTable(switchId) -> [{ mac, port }]                   // learned from traffic so far
net.l2Domain(devId) -> [devIds]                             // hosts/routers reachable at layer 2 (same broadcast domain)
NetSim.ip  // helpers: parse(str)->int|null, str(int), mask(prefix), prefixFromMask(str)->int|null, inSubnet(ip,net,prefix),
           // network(ip,prefix), broadcast(ip,prefix), isPrivate, classOf, hostsIn(prefix)
NetSim.render(topo, { width, height, highlight: [devIds], showIp: true }) -> SVG string   // static drawing
          // simple icons per type, labels "PC1\n192.168.1.10/24", links as lines (dashed for wifi, red X for down),
          // colors via CSS variables only. Used by the bank's "network diagram analysis" questions.
```

`reason` codes for ping (first failure that applies, evaluated like a real stack):
`ok`, `iface_down` (adapter disabled), `no_link` (cable unplugged/broken → Windows "General failure." /
"PING: transmit failed. General failure."), `no_ip`, `bad_target` (could not find host: name not resolvable),
`dns_fail`, `same_subnet_unreachable` (ARP fails on local subnet → Windows "Reply from <own ip>: Destination host
unreachable."), `no_gateway` (remote target, no gateway → Windows "PING: transmit failed. General failure."),
`gateway_unreachable` (ARP for gateway fails → "Reply from <own ip>: Destination host unreachable."),
`no_route` (router has no route → "Reply from <router ip>: Destination net unreachable."),
`timeout` (packet reaches destination but reply cannot come back, e.g. destination's gateway wrong, or target
firewall drops ICMP → "Request timed out."), `ttl_expired` (routing loop → "Reply from <router ip>: TTL expired in transit.").
Ping to own IP and 127.0.0.1 succeed whenever the adapter is enabled (127.0.0.1 even when no link).

### 3.3 Output formats (must look real)

Windows `ping 192.168.1.20`:
```
Pinging 192.168.1.20 with 32 bytes of data:
Reply from 192.168.1.20: bytes=32 time<1ms TTL=128
...
Ping statistics for 192.168.1.20:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
Approximate round trip times in milli-seconds:
    Minimum = 0ms, Maximum = 1ms, Average = 0ms
```
TTL: Windows hosts 128, Linux servers 64 (server may set `os:'linux'`), routers 255; decrement 1 per router hop.
Times deterministic (e.g. 0–2 ms LAN, +1 ms per router, ~20 ms internet). Note Windows counts "Destination host
unreachable" replies as *Received* in statistics (real behaviour). Linux `ping -c 4` format:
`PING 192.168.1.20 (192.168.1.20) 56(84) bytes of data.` / `64 bytes from 192.168.1.20: icmp_seq=1 ttl=64 time=0.41 ms` /
`--- 192.168.1.20 ping statistics ---` / `4 packets transmitted, 4 received, 0% packet loss, time 3004ms`, and
`From 192.168.1.10 icmp_seq=1 Destination Host Unreachable`, `ping: www.x.test: Name or service not known`,
`ping: connect: Network is unreachable` (no route/gateway).
Windows `tracert` and Linux `traceroute` similarly realistic (`*` lines and "Request timed out." on silent hops,
max 30 hops; stop after 4 consecutive timeouts in the simulator and print `Trace complete.` only on success).
`nslookup`: `Server:  dns.lab.local` / `Address:  192.168.1.5` / `Non-authoritative answer:` / `Name: ...` / `Address: ...`,
errors `*** dns.lab.local can't find x: Non-existent domain` and `DNS request timed out.` when the server is unreachable.

## 4. Simulator requirements

### 4.1 Network Topology Simulator (`topology`)
- Canvas (SVG) with a palette: PC, Laptop, Server, Printer, Switch, Router, Access Point, Internet.
  Drag from palette to place; drag to move; select to edit; delete. Connect: choose "สายสัญญาณ" tool (UTP/Fiber/Wi-Fi)
  then click device A then device B — pick free ports automatically (show port names). Click a link to delete it or
  toggle up/down.
- Property panel for the selected device: name, IP/prefix (also accept dotted mask), gateway, DNS, DHCP on/off,
  router interfaces + static routes, DHCP/DNS services on servers, AP SSID. Validate inline (Thai messages).
- Problems panel = `net.problems()` live.
- "ส่ง Ping" tool: choose source + target (IP or name) → run `net.ping`, animate a packet dot along `path`
  (respect prefers-reduced-motion), show the Windows output, and mark success/failure with the reason in Thai.
- Zoom/pan or a fixed large canvas with scroll; touch works. Undo (at least 20 steps). Autosave draft.
- Free-play mode + missions. Missions (grader checks with netsim, server side):
  t1 two PCs + switch, same subnet, ping each other; t2 small lab: 1 switch, 4 PCs, 1 printer, all reach each other,
  no duplicate IPs; t3 add a router and internet: PCs reach 8.8.8.8 (gateway + default route); t4 two subnets
  (two switches, router with 2 LAN interfaces), cross-subnet ping both ways; t5 DHCP: server with DHCP pool, PCs set
  to DHCP get addresses and reach the server; t6 wireless: AP + 2 laptops on the right SSID reach a wired server;
  t7 DNS: PCs resolve `srv.lab.local` and `www.netlab.test` by name. Each mission's `start` may provide a partial
  topology. Grader: build net, check required device types/counts, run the required pings server-side, give
  partial credit per requirement, and feedback per failed requirement.

### 4.2 Subnetting Simulator (`subnet`)
- Missions are practice sets by level: easy (classful /8 /16 /24 and /25–/26 on class C), medium (/17–/30 any class,
  find network/broadcast/first/last/hosts/mask), hard (VLSM: given a block and host requirements for 3–5 subnets,
  allocate largest-first, give network/prefix for each; also "how many subnets of /x fit in /y").
- `generate(missionId, rand)` creates a problem (no answers inside); the browser asks `ctx.newProblem`, the student fills
  answers, `ctx.submit(missionId, {answers}, {problem, token})`. Grade per field (partial credit).
- After grading show a **step-by-step solution** (binary of the interesting octet, block size, how network/broadcast
  were found) computed in the browser from the problem (it is fine for the browser to compute the solution
  after submit). Also a "เครื่องคิดเลขช่วยคิด" free mode with step display, and a binary helper (128 64 32 16 8 4 2 1).
- Accept dotted mask or /prefix where asked; ignore spaces.

### 4.3 UTP Crimping Simulator (`crimp`)
- Realistic sequence: choose standard per end (T568A/T568B), strip jacket (choose length slider), untwist and arrange
  8 wires by **dragging** colored wires into slots 1–8 (touch + keyboard alternative: select wire then slot),
  trim length (slider: untwisted length, mm), insert into RJ-45 (jacket must reach inside the plug), crimp, then test
  with a LAN tester animation (LEDs 1–8 lighting in sequence on both ends).
- The tester result is computed from the actual wiring of both ends: straight-through (1→1..8→8), crossover
  (1→3, 2→6, 3→1, 6→2, others same), miswire, open (missing/short wire), and **split pair** (pins correct 1–8 continuity
  but pair grouping wrong, e.g. wiring 1-2-3-4-5-6-7-8 with colors in a non-standard order on both ends: the basic LED
  tester shows "pass" but explain that a split pair causes crosstalk — show a warning only if the student uses
  "เครื่องทดสอบขั้นสูง").
- Errors with explanation (Thai): wrong color order (which pins), untwisted length > 13 mm (crosstalk / not to
  standard), jacket not inside the plug (cable pulls out), wires not trimmed evenly, standards mismatch for the
  mission (e.g. asked for straight-through but built crossover).
- Missions: c1 T568B straight-through, c2 T568A straight-through, c3 crossover (A–B), c4 "find the fault": a
  pre-built cable is given (start data) and the student tests it and chooses what is wrong (open pin / miswire /
  split pair / reversed), c5 make a patch cable to the lab's rule (T568B both ends, untwist ≤ 13 mm).
- Grader receives `{ end1: { standardChoice, order: [8 color codes], strip_mm, untwist_mm, jacketInside, trimmed },
  end2: {...}, diagnosis? }`. Color codes: `wo o wg bl wb g wbr br` (white-orange, orange, white-green, blue,
  white-blue, green, white-brown, brown).

### 4.4 Network Terminal Simulator (`terminal`)
- A terminal UI (Windows Command Prompt look or Linux bash look depending on the host) bound to a NetSim network.
  The student picks which host to sit at (from the scenario), types commands; outputs come from NetSim.
- Windows: `ipconfig`, `ipconfig /all`, `ipconfig /release`, `ipconfig /renew`, `ipconfig /flushdns`, `ping [-n N] [-t is
  refused politely] target`, `tracert target`, `nslookup name [server]`, `arp -a`, `route print`, `netstat -an`
  (simulated connections from scenario data), `hostname`, `getmac`, `cls`, `help`. Linux: `ip addr` / `ip a`,
  `ip route`, `ip link set eth0 up|down` (root only), `ping -c N target`, `traceroute target`, `nslookup name`,
  `dig name` (short), `cat /etc/resolv.conf`, `hostname`, `whoami`, `clear`, `help`. Unknown commands give the
  real error ("'x' is not recognized as an internal or external command, ..." / "bash: x: command not found").
- History with ↑/↓, Tab completion of command names, copy-friendly output, quick buttons for mobile.
- Missions = scenarios (`start` contains topology + the host the student sits at + a short story) with questions the
  student answers by investigating (e.g. "IP ของ default gateway คืออะไร", "เครื่องนี้ได้ IP จาก DHCP หรือไม่",
  "hop ที่ 2 ของเส้นทางไปยัง 8.8.8.8 คือ IP ใด", "DNS server ตอบชื่อ srv.lab.local เป็น IP อะไร"). Answers are typed
  into fields and graded on the server (answer key lives only in the server grader). 6–8 scenarios mixing Windows and Linux.
- The grader can also accept `commandsUsed: [strings]` and award a small part of the score for using an appropriate
  command (e.g. ipconfig /all for DNS server question) — optional.

### 4.5 Network Troubleshooting Lab (`troubleshoot`)
- Scenario-based: each mission has a story ("ห้องคอม 3: PC7 เข้าเว็บไม่ได้ แต่เพื่อนเข้าได้"), a topology with exactly
  one or two injected faults (`start.topo`), and a list of possible causes.
- The student investigates with a built-in terminal (reuse NetSim; a compact terminal is fine — may load
  `public/js/sim/terminal.js` helpers if present, but must work standalone), and by viewing device settings
  (read-only view of IP config, cable status lights, router routes).
- Then the student (1) chooses the root cause from 5–7 options, (2) applies a fix in an edit panel (change the faulty
  setting, plug a cable, enable an adapter, add a route, fix DNS), (3) verifies with ping, (4) submits.
- Grader: payload `{ cause, topo }`. Score = cause correct (40%) + fix verified (60%): the submitted topology must be
  the scenario topology with only allowed edits (compare structurally: same devices and links; changed fields must be in
  the mission's allowed list, otherwise "แก้ไขเกินขอบเขต") and the mission's success pings must pass in NetSim, and the
  fault must actually be fixed (not worked around, e.g. giving the PC a different subnet).
- 7–8 scenarios covering: unplugged cable (`no_link`), wrong gateway, wrong subnet mask, duplicate IP, wrong DNS,
  DHCP server down → APIPA, router missing route to another subnet, disabled adapter, wrong Wi-Fi SSID, host
  firewall blocking ping (and explain ping fails but web works — teach that ping failing is not always a network fault).
