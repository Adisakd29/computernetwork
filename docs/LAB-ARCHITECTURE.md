# สถาปัตยกรรมห้องปฏิบัติการเสมือน (NetLab 2.8)

เอกสารนี้แยกให้ชัดว่าแล็บแต่ละอย่างใน NetLab เป็นระดับใด ตามข้อกำหนด "ห้ามเรียก Terminal ที่มีข้อความผลลัพธ์จำลองว่าเป็น Virtual Machine จริง" และสรุปทางเลือกถ้าจะขยายไปสู่ห้องแล็บแบบเครื่องจริงบนเซิร์ฟเวอร์

## 1. สามระดับของแล็บ

| ระดับ | ความหมาย | ทำงานที่ไหน | ตรวจคะแนนอย่างไร |
|---|---|---|---|
| A. Visualization | สื่อโต้ตอบที่แสดงหลักการ ผู้เรียนปรับค่าแล้วเห็นผลทันที | เบราว์เซอร์ | ไม่ให้คะแนน (หรือมีคำถามตรวจความเข้าใจแยก) |
| B. Stateful simulator | ระบบจำลองที่มีสถานะจริง คำนวณผลจากสิ่งที่ผู้เรียนตั้งค่า (ไม่ใช่ข้อความสำเร็จรูป) | เบราว์เซอร์ + เซิร์ฟเวอร์ตรวจซ้ำ | เซิร์ฟเวอร์คำนวณใหม่จากข้อมูลที่ส่งมา ผู้เรียนแก้คะแนนเองไม่ได้ |
| C. Real VM | ระบบปฏิบัติการจริงที่รันคำสั่งจริง | เครื่องของผู้เรียน (WebAssembly) | ตอบคำถามจากผลคำสั่งจริงในห้องฝึก |

### ระดับ A: Visualization
- แผนภาพและสื่อโต้ตอบในบทเรียน (`public/js/diagrams*.js`, `widgets*.js`, `figs-a`…`figs-g.js`)
- สื่อใหม่ใน 2.8 ส่วนใหญ่อยู่ระดับนี้ แต่ใช้ตรรกะคำนวณจริง เช่น
  - ปรับสัญญาณ (แอมพลิจูด/ความถี่/เฟส) และ Multiplexing
  - คำนวณ Parity / Checksum / CRC จากบิตจริง
  - ARQ (Stop-and-Wait / Go-Back-N / Selective Repeat) ตามลำดับเฟรมที่หาย
  - เข้ารหัสแบบ Caesar/XOR และตรวจใบรับรอง (Certificate) จำลอง
  - TCP state, Socket demultiplexing, Circuit/Packet switching, Jitter buffer
  - เทอร์มินัลอนุกรม RS-232 จำลอง

### ระดับ B: Stateful simulator
- **ห้องจำลองเครือข่าย (topology)** ใช้เอนจิน NetSim (`public/js/sim/netsim.js`) ซึ่งใช้ไฟล์เดียวกันทั้งเบราว์เซอร์และเซิร์ฟเวอร์ ทำงานได้จริงดังนี้
  - ตาราง MAC ของ Switch และ Hub แบบส่งทุกพอร์ต (Collision domain)
  - ARP, Routing (static/default), DHCP, DNS และกฎ Firewall ของ Router
  - Wi-Fi ที่มีรหัสผ่านและ Client isolation
  - การปิดเครื่อง (Power off)
  - ผล ping และ tracert คำนวณจากแผนผังจริง
- **โครงงานปิดท้าย t9 (สัปดาห์ 18)**
  - ออกแบบเครือข่ายวิทยาลัย 3 ห้อง พร้อม VLSM, Gateway/DNS, Firewall, Wi-Fi และ Connectivity matrix
  - ระบบใส่เหตุขัดข้องให้ แล้วให้ผู้เรียนแก้และเขียนรายงาน
  - คะแนนอัตโนมัติ 40 ตาม Rubric 10 ข้อ ครูตรวจรายงานเพิ่มได้
- **ห้อง Subnet**: โจทย์สุ่มลงลายเซ็น HMAC
- **ห้องเข้าหัวสาย (crimp)**
- **เทอร์มินัล Windows จำลอง (terminal)**
  - เป็นตัวแปลคำสั่งที่คำนวณผลจากสถานะเครือข่ายจำลอง
  - **ไม่ใช่ Virtual Machine** และหน้าเว็บไม่ได้เรียกว่า VM
- **ห้องแก้ไขปัญหา (troubleshoot)**
  - x1–x13 เป็นสถานการณ์คงที่
  - **x14 สุ่มเหตุขัดข้อง 1–2 จุดจากเซิร์ฟเวอร์** โจทย์ลงลายเซ็น และเฉลยถูกสร้างใหม่จาก nonce ด้วยกุญแจลับบนเซิร์ฟเวอร์
  - ผู้เรียนต้องเก็บหลักฐาน แก้ไข ทดสอบซ้ำ และเขียนรายงาน
  - คะแนนอัตโนมัติ 20 บวกครูตรวจรายงาน 8 คะแนน

### ระดับ C: Real VM
- **Linux VM ด้วย v86** เป็นเครื่อง x86 จำลองด้วย WebAssembly
  - บูต Linux (buildroot) จริง และรันคำสั่ง `ip`, `ls`, `chmod` ฯลฯ จริง
  - ใช้ในห้องฝึก r5, r9, r10, r11, r12 และแล็บสัปดาห์ที่มีป้าย Linux VM
- **รันบนเครื่องของนักเรียนแต่ละคน** ไม่ได้รันบนเซิร์ฟเวอร์ จึงไม่เพิ่มภาระ Railway
- **ไม่ได้ต่อการ์ดเครือข่ายออกภายนอก**
  - ไม่ได้ตั้ง `network_relay_url` จึงไม่มีทางส่งแพ็กเก็ตออกอินเทอร์เน็ตหรือเครือข่ายวิทยาลัย
  - ฝึกได้เฉพาะการตั้งค่าภายในเครื่อง เช่น loopback, ไฟล์ และสิทธิ์
- ข้อจำกัด
  - ต้องโหลดไฟล์ VM ประมาณ 10–20 MB ครั้งแรก
  - ต้องใช้เครื่องที่มี RAM ว่างอย่างน้อยประมาณ 256 MB
  - บนมือถือรุ่นเก่าอาจช้า
  - ไม่มีเครือข่ายหลายเครื่องให้ทดลอง routing ระหว่าง VM จริง

## 2. ทางเลือกถ้าต้องการแล็บระดับ C ที่มีเครือข่ายหลายเครื่อง

Railway (โฮสต์ปัจจุบัน) ไม่อนุญาต privileged container และ nested virtualization จึงสร้าง network namespace หรือ VM ซ้อนในคอนเทนเนอร์ของแอปไม่ได้ ต้องเลือกจากทางด้านล่าง

**ราคาเป็นค่าประมาณ ณ ปี 2026 ต้องตรวจราคาจริงก่อนตัดสินใจ**

### ทางเลือก 1: v86 หลายเครื่องในเบราว์เซอร์ (ต่อกันด้วย virtual switch ในหน้าเว็บ)

**ข้อดี**
- ไม่มีค่าใช้จ่ายเพิ่ม
- แยกขาดจากเครือข่ายจริงโดยธรรมชาติ
- ไม่มีภาระเซิร์ฟเวอร์

**ข้อเสีย**
- ใช้ RAM ประมาณ 128 MB ต่อ VM บนเครื่องนักเรียน 2–3 เครื่องก็หนักสำหรับมือถือ
- ต้องพัฒนา network adapter แบบ in-page relay เพิ่ม
- บูตช้า

**ค่าใช้จ่าย:** 0 บาท (เวลาพัฒนาเท่านั้น)

### ทางเลือก 2: คอนเทนเนอร์ต่อผู้เรียนบน Railway

ผู้เรียนแต่ละคนได้คอนเทนเนอร์ Alpine ของตัวเอง

**ข้อดี**
- ใช้ Linux จริงบนเซิร์ฟเวอร์
- เปิดจากมือถือได้

**ข้อเสีย**
- สร้างหลายเครื่องที่ต่อกันเป็นเครือข่ายไม่ได้ (ไม่มีสิทธิ์สร้าง namespace หรือ veth)
- ต้องมีระบบสร้างและลบบริการผ่าน API
- เสี่ยงค่าใช้จ่ายบานปลายถ้าลืมลบ
- ต้องกันการออกอินเทอร์เน็ตเอง

**ค่าใช้จ่าย:** ประมาณ 0.25 GB RAM ต่อคนต่อชั่วโมง ห้อง 40 คน × 2 ชั่วโมงต่อสัปดาห์ น่าจะอยู่ราว 5–15 USD ต่อเดือน ตามอัตรา usage-based ของ Railway

### ทางเลือก 3: VPS แยกสำหรับแล็บ (แนะนำถ้าจะทำจริง)

ใช้ VPS ที่อนุญาต namespace แล้วรัน Containerlab หรือ Mininet สร้างเครือข่ายย่อยต่อผู้เรียนเป็นช่วงเวลา และให้ผู้เรียนเข้าผ่าน Web terminal

**ข้อดี**
- ได้ routing, VLAN และ firewall จริงหลายเครื่อง
- ควบคุมการแยกเครือข่ายได้เต็มที่

**ข้อเสีย**
- ต้องดูแลเซิร์ฟเวอร์เพิ่มอีกเครื่อง
- ต้องมีระบบจองเวลาและล้างแล็บอัตโนมัติ
- ต้องทำ Hardening อย่างจริงจัง

**ค่าใช้จ่าย:** VPS 4 vCPU / 8 GB ประมาณ 10–25 USD ต่อเดือน รองรับผู้เรียนพร้อมกันราว 20–40 คน ถ้าใช้คอนเทนเนอร์ Linux เบา ๆ (ไม่ใช่ image ของ router เชิงพาณิชย์)

### ทางเลือก 4: Remote lab ชั่วคราว (สร้างเมื่อเริ่มคาบ ลบเมื่อจบคาบ)

ใช้ทางเลือก 3 แต่เปิดเครื่องแบบคิดค่าบริการรายชั่วโมงเฉพาะช่วงคาบเรียน

**ข้อดี**
- ประหยัดที่สุดเมื่อใช้ไม่บ่อย

**ข้อเสีย**
- ต้องมีสคริปต์สร้างเครื่องอัตโนมัติ
- ใช้เวลาเปิดเครื่องหลายนาทีก่อนคาบ

**ค่าใช้จ่าย:** ประมาณ 0.03–0.06 USD ต่อชั่วโมง × ชั่วโมงที่ใช้จริง

**ข้อเสนอ:** ใช้ระดับ B (NetSim) เป็นหลักต่อไป เพราะทำงานบนมือถือได้ ตรวจคะแนนได้ และไม่มีค่าใช้จ่าย ใช้ระดับ C ที่มีอยู่ (v86) สำหรับคำสั่ง Linux ถ้าวิทยาลัยต้องการ routing หรือ VLAN บนระบบจริง ให้พิจารณาทางเลือก 3 หรือ 4 โดย**ยังไม่ได้พัฒนาส่วนนี้ใน 2.8**

## 3. ข้อกำหนดความปลอดภัยที่ต้องคงไว้ (ทุกระดับ)

- **ห้ามออกเครือข่ายภายนอก**
  - แล็บทุกแบบต้องแยกจากอินเทอร์เน็ตและเครือข่ายวิทยาลัย
  - v86 ไม่มี relay
  - NetSim เป็นการคำนวณล้วน
  - ถ้าทำทางเลือก 3 หรือ 4 ต้องตั้ง egress firewall แบบ deny-all และใช้บริดจ์ภายในเท่านั้น
- **เครื่องมือความปลอดภัยใช้ในระบบจำลองเท่านั้น**
  - กิจกรรมด้านความปลอดภัยใน NetLab เป็นการป้องกัน ได้แก่ Firewall, รหัสผ่าน Wi-Fi, การเข้ารหัส และการตรวจใบรับรอง
  - ทั้งหมดทำในระบบจำลองที่ได้รับอนุญาต
  - ไม่มีเครื่องมือสแกนหรือโจมตีเป้าหมายจริง
- **คะแนนคิดที่เซิร์ฟเวอร์**
  - ทุกภารกิจระดับ B ตรวจซ้ำบนเซิร์ฟเวอร์
  - โจทย์สุ่มลงลายเซ็น HMAC ผูกกับผู้ใช้และหมดอายุใน 6 ชั่วโมง
  - คะแนนครูตรวจได้เฉพาะครูเจ้าของห้อง และตรวจช่วงคะแนน 0–max
- **ข้อจำกัดของทรัพยากร**
  - payload สูงสุด 300 KB ต่อการส่ง
  - จำกัดอัตราการส่งที่ 60 ครั้งต่อนาทีต่อผู้ใช้ หรือ 1,200 ครั้งต่อนาทีต่อ IP สำหรับผู้เยี่ยมชม
  - เก็บงานที่ต้องตรวจเพียง 5 ครั้งล่าสุดต่อผู้เรียนต่อภารกิจ
- **ช่องว่างที่ทราบ**
  - เหตุขัดข้องใน t9 คำนวณแบบ deterministic จากแผนผังที่ผู้เรียนสร้างสำเร็จครั้งแรก (เซิร์ฟเวอร์คำนวณซ้ำได้) แต่ไม่ได้สุ่มจากเซิร์ฟเวอร์เหมือน x14
  - ผู้เรียนที่แก้คำขอ HTTP เองอาจส่งแผนผังตั้งต้นที่ทำให้ได้เหตุขัดข้องแบบที่ตนต้องการ
  - ส่วนนี้มีน้ำหนักเพียง 3 จาก 40 คะแนน และครูตรวจรายงานประกอบ
