# Migration Plan: ระบบเรียนตามลำดับ (Progressive Unlock) เวอร์ชัน 2.15.0

## 1. หลักการ

- **ไม่ลบ ไม่รีเซ็ต และไม่แก้คะแนนเดิม**
  - คะแนนก่อน/หลังเรียน การอ่านเนื้อหา แบบฝึกหัด ผลห้องจำลอง และ XP อยู่ครบ
- **ห้องเรียนที่มีอยู่แล้วทำงานเหมือนเดิมจนกว่าครูจะเปิดเอง**
  - การเรียนตามลำดับยังปิดอยู่
  - สอบหลังเรียนได้ 1 ครั้งและเห็นเฉลยทันที เหมือนเดิม
- **ห้องเรียนใหม่ที่สร้างหลัง deploy เปิดการเรียนตามลำดับอัตโนมัติ**
  - ใช้ค่าเริ่มต้นใน `content/learning-path.js`
  - นักเรียนที่ไม่มีห้องเรียนก็ใช้ค่าเริ่มต้นนี้ และเรียนตามลำดับเช่นกัน
- **เมื่อครูเปิดการเรียนตามลำดับให้ห้องเดิม ไม่มีนักเรียนคนใดถูกล็อกออกจากงานที่ทำไปแล้ว**
  - ระบบตรวจงานเดิมก่อน แล้วสัปดาห์ที่นักเรียน "เคยเริ่มทำ" ไว้แต่ยังไม่ถึงตามลำดับจะคงเปิดไว้
  - การเปิดแบบนี้บันทึกเป็นชนิด `legacy` ในประวัติการปลดล็อก
  - ครูเห็นรายชื่อทันทีหลังกดบันทึก และเพิกถอนได้ทีละรายการ
- **สัปดาห์ที่ผ่านแล้วจะผ่านตลอดไป**
  - สัปดาห์ที่ผ่านเงื่อนไขแล้วถูกบันทึกเป็น Completed ใน `week_completions`
  - การเพิ่มเกณฑ์ภายหลังไม่ทำให้สัปดาห์ที่ผ่านแล้วกลับไปล็อก

## 2. สิ่งที่เปลี่ยนในฐานข้อมูล

ทุกรายการเป็นการเพิ่มอย่างเดียว อยู่ท้าย `server/schema.sql` และรันซ้ำได้

| การเปลี่ยน | รายละเอียด | ผลต่อข้อมูลเดิม |
|---|---|---|
| คอลัมน์ `classes.path JSONB` | กติกาของห้อง: เปิด/ปิดการเรียนตามลำดับ, เกณฑ์ %, เงื่อนไข, จำนวนครั้งสอบ, เวลารอ, วันเปิดบทเรียน | ห้องเดิมได้ค่าแบบเดิม (ดูข้อ 3) |
| ตาราง `week_completions` | สัปดาห์ที่ผ่านแล้ว และเงื่อนไขขณะผ่าน | ไม่มี |
| ตาราง `path_unlocks` | การเปิดบทเรียนเพิ่มโดยครู (`teacher`), การคงงานเดิม (`legacy`) และประวัติการแก้กติกา (`settings`) มีคอลัมน์ `revoked_at` จึงไม่มีการลบประวัติ | ไม่มี |
| ตาราง `path_activation` | บันทึกว่าตรวจงานเดิมของนักเรียนคนนี้แล้ว (ทำครั้งเดียวต่อคนต่อห้อง) | ไม่มี |
| ตาราง `quiz_attempt_log` | ประวัติการสอบหลังเรียนทุกครั้ง ส่วน `quiz_attempts` ยังเก็บคะแนนที่ดีที่สุด | ไม่มี คะแนนเดิมถูกคัดลอกเป็นครั้งที่ 1 เมื่อนักเรียนสอบใหม่ครั้งแรก |

ทุกตารางอ้างอิง `users(id) ON DELETE CASCADE` เมื่อลบบัญชี ข้อมูลเส้นทางการเรียนของคนนั้นจะถูกลบไปด้วย เหมือนคะแนนอื่น

## 3. การแปลงข้อมูลเดิม (data migration)

ทำครั้งเดียว และบันทึกใน `app_migrations` ด้วย id `path-1`

- **ห้องเดิม:** ทุกห้องที่ `path` เป็น NULL จะได้ค่าต่อไปนี้ (`LEGACY_CLASS` ใน `content/learning-path.js`)
  ```json
  { "sequential": false, "post": { "maxAttempts": 1, "cooldownMin": 0, "review": "always" } }
  ```
  ส่วนอื่นเป็นค่าเริ่มต้น
- **log ตอนเริ่มเซิร์ฟเวอร์:** `Progressive Unlock: N existing class(es) keep their previous behaviour until the teacher turns sequential learning on`
- **ห้องที่สร้างหลังจากนี้:** ไม่ถูกแตะ จึงเรียนตามลำดับ

**การตรวจงานเดิม (ทำเมื่อครูเปิดการเรียนตามลำดับ หรือเมื่อนักเรียนเข้าใช้ครั้งแรกในห้องที่เปิดอยู่)**
- ระบบไล่สัปดาห์ 1 ถึง 18 ตามกติกาใหม่
- สัปดาห์ใดที่ยังไม่ถึงตามลำดับ แต่นักเรียนมีร่องรอยการเรียนแล้ว จะได้รายการ `legacy`
  - ร่องรอยคือ: อ่านเนื้อหา ทำแบบฝึกหัด สอบก่อนหรือหลังเรียน หรือทำงานในแล็บท้ายคาบของสัปดาห์นั้น
- สัปดาห์ที่ยังไม่เคยแตะยังล็อกตามปกติ

**กรณีที่ครูควรตรวจ (ข้อมูลขัดแย้ง)**
- นักเรียนที่เคยเรียนข้ามสัปดาห์จะเห็นสัปดาห์ที่ข้ามไปเป็น "พร้อมเรียน" และสัปดาห์ที่เรียนล่วงหน้าเป็น "กำลังเรียน"
- ครูดูรายชื่อได้ 3 ที่: รายงานหลังบันทึกกติกา, คอลัมน์ "เปิดพิเศษ" ในตารางนักเรียน (ข้อความ "เรียนไว้ก่อน") และประวัติการปลดล็อก
- ครูเลือกได้ว่าจะคงไว้ หรือกด "เพิกถอน" เพื่อให้นักเรียนกลับมาเรียนตามลำดับ
- คะแนนที่ทำไปแล้วไม่หายไม่ว่าเลือกแบบใด

## 4. ขั้นตอน deploy (ทำตามลำดับ)

1. **สำรองแบบกู้คืนได้**
   ```
   pg_dump "$DATABASE_URL" -Fc -f netlab-before-2.15.dump
   ```
   บน Railway ใช้ `DATABASE_PUBLIC_URL` ของบริการ Postgres เมื่อรันจากเครื่องตัวเอง
2. **สำรองแบบอ่านได้**
   ```
   DATABASE_URL="..." node scripts/backup-db.js netlab-before-2.15.json.gz
   ```
   ไฟล์ทั้งสองมีข้อมูลส่วนบุคคล ห้าม commit และห้ามส่งต่อ
3. **Deploy 2.15.0** นอกเวลาเรียน
   - log ต้องมี `Database ready.` และบรรทัด Progressive Unlock ในข้อ 3
4. **ตรวจหลัง deploy**
   ```
   DATABASE_URL="..." node scripts/backup-db.js --verify netlab-before-2.15.json.gz
   ```
   - ตารางเดิมต้อง `same`
   - ยกเว้น `app_migrations` ที่เพิ่ม 1 แถว (`path-1`)
   - และตารางที่มีการใช้งานระหว่าง deploy ซึ่งแถวเพิ่มได้ แต่ห้ามลด
5. **เปิดใช้ทีละห้อง**
   1. หน้าครู → ห้องเรียน → แท็บ "เส้นทางการเรียน"
   2. ตรวจกติกา แล้วเปิด "เรียนตามลำดับ"
   3. อ่านรายงานนักเรียนที่มีสัปดาห์เปิดจากงานเดิม

## 5. การย้อนกลับ (Rollback)

- **ย้อนเฉพาะโค้ด (แนะนำ):** deploy 2.14.0 กลับไป
  - โค้ดเก่าไม่อ่านคอลัมน์และตารางใหม่ ทุกบทเรียนจึงเปิดเหมือนเดิม
  - การสอบหลังเรียนกลับเป็นแบบครั้งเดียว และคะแนนที่ดีที่สุดยังอยู่ใน `quiz_attempts`
  - ถ้ากลับมาใช้ 2.15.0 สถานะ Completed และประวัติยังอยู่ครบ
- **ปิดการล็อกโดยไม่ย้อนโค้ด:** ปิด "เรียนตามลำดับ" ในห้องนั้น นักเรียนเข้าได้ทุกสัปดาห์ทันที และข้อมูลไม่หาย
- **ย้อนโครงสร้าง:** ใช้เมื่อจำเป็นจริงเท่านั้น เพราะประวัติการสอบซ้ำและการปลดล็อกจะหายถาวร
  ```sql
  DROP TABLE IF EXISTS quiz_attempt_log, path_activation, path_unlocks, week_completions;
  ALTER TABLE classes DROP COLUMN IF EXISTS path;
  DELETE FROM app_migrations WHERE id = 'path-1';
  ```
- **กู้คืนทั้งฐานข้อมูล:**
  ```
  pg_restore --clean --if-exists -d "$DATABASE_URL" netlab-before-2.15.dump
  ```

## 6. ผลการซ้อม Migration (รันจริงในเครื่องทดสอบ 14 ต.ค. 2026)

สคริปต์อยู่ในเครื่องทดสอบ ไม่ได้อยู่ในโปรเจกต์

1. **สร้างข้อมูลด้วยโค้ดเวอร์ชันเก่า 2.14.0** ในฐานข้อมูลใหม่ `netlab_migp`: ครู 1 คน ห้อง 1 ห้อง นักเรียน 3 คน ทำงานผ่าน API จริง
   - คนที่ 1 ผ่านสัปดาห์ 1–2 ครบทุกเงื่อนไข และอ่านสัปดาห์ 3 ไปบางส่วน
   - คนที่ 2 ผ่านสัปดาห์ 1 แล้ว**ข้าม**สัปดาห์ 2 ไปอ่านสัปดาห์ 4 และสอบหลังเรียนสัปดาห์ 5 ได้ 10 คะแนน
   - คนที่ 3 ยังไม่เริ่ม
2. **สำรองข้อมูลทั้ง 2 แบบ** ด้วย `pg_dump -Fc` และ `backup-db.js`
3. **เปิดเซิร์ฟเวอร์ 2.15.0 บนฐานข้อมูลนี้**
   - log: `Progressive Unlock: 1 existing class(es) keep their previous behaviour ...` แล้ว `Database ready.`
4. **`backup-db.js --verify`** ได้ `same` ทุกตารางเดิม ยกเว้น `app_migrations` (1 → 2 แถว)
5. **เทียบเนื้อหาทุกแถวก่อนและหลัง:** มี 2 ตารางที่ต่าง และต่างตามแผน
   - `app_migrations` เพิ่มแถว `path-1`
   - `classes` เพิ่มค่า `path` ตามข้อ 3
   - ตารางคะแนนทุกตารางไม่เปลี่ยน
   - ตารางใหม่ 4 ตาราง
6. **ก่อนครูเปิดระบบ:** `sequential=false`, `maxAttempts=1` นักเรียนเข้าได้ทุกสัปดาห์เหมือนเดิม
7. **ครูเปิด "เรียนตามลำดับ"** (ผ่าน API ด้วยบัญชีผู้ดูแล)
   - รายงานแสดงนักเรียนคนที่ 2 มีสัปดาห์ที่เปิดจากงานเดิม `w4, w5`
   - ผลรายคน (C = ผ่าน, P = กำลังเรียน, A = พร้อมเรียน, L = ล็อก):

     | นักเรียน | สัปดาห์ 1–7 | สัปดาห์ปัจจุบัน | หมายเหตุ |
     |---|---|---|---|
     | คนที่ 1 | `CCPLLLL` | 3 | |
     | คนที่ 2 | `CALPPLL` | 2 | สัปดาห์ 4–5 ยังเข้าได้ สัปดาห์ 3 และ 6 ล็อก |
     | คนที่ 3 | `ALLLLLL` | 1 | |

   - ประวัติมี `legacy:w4`, `legacy:w5` และ `settings:*`
   - `week_completions` มีสัปดาห์ 1–2 ของคนที่ 1 และสัปดาห์ 1 ของคนที่ 2 ไม่มีใครเสียสัปดาห์ที่ผ่านแล้ว
8. **ซ้อมย้อนโค้ด:** เปิดเซิร์ฟเวอร์ 2.14.0 บนฐานข้อมูลที่อัปเกรดแล้ว
   - เริ่มทำงานปกติ ล็อกอินได้ และอ่านรายชื่อห้องได้
   - `GET /api/lessons/w10` ตอบ 200 คือไม่มีการล็อกแบบเดิม
9. **ซ้อมสำรองและกู้คืนแบบไบนารี:** `pg_dump -Fc` ฐานข้อมูลที่อัปเกรดแล้ว จากนั้น `pg_restore` ลงฐานข้อมูลใหม่ และตรวจด้วย `--verify` ได้ `same` ครบ 30 ตาราง

**ข้อที่ยังไม่ได้ทำ:** ยังไม่ได้ทดสอบกับฐานข้อมูลจริงบน Railway ขั้นที่ 1–2 ของข้อ 4 ต้องทำบนระบบจริงก่อน deploy
