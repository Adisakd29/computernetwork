**สัปดาห์หลักเลือกจากจุดประสงค์ของบทเรียน** ส่วนใหญ่ตรงกับ mapping ที่ครูให้ไว้ ที่ต่างไปมีเหตุผลดังนี้

- **ห้อง 5 → สัปดาห์ 8:** เพราะเป็นบทการตั้งค่า IPv4 และตรงกับ VM `ip addr` ส่วนสัปดาห์ 3 (คลาส IP) ลิงก์ถึง
- **ห้อง 9 → สัปดาห์ 9:** ข้อที่เหลือเป็นเรื่องเครือข่ายใน Windows ส่วน VM อยู่แล้วในแล็บสัปดาห์ 12

**สัปดาห์ที่ลิงก์ถึง** แสดงภารกิจเดียวกัน (ลิงก์ ไม่ใช่สำเนา) ทำครั้งเดียว คะแนนนับที่เดียว

**ลดเวลาจับเวลาของห้อง 9–12** เพราะส่วน VM ย้ายไปอยู่แล็บท้ายคาบ และข้อซ้ำถูกซ่อน
- มีผลกับการเริ่มทำครั้งใหม่เท่านั้น
- รอบที่เริ่มไปแล้วยังใช้กำหนดส่งเดิมที่บันทึกในฐานข้อมูล

## 4. Linux VM ครบ 27 ข้อ

| ภารกิจ VM | จำนวน | ทำที่ |
|---|---|---|
| ห้อง 5 | 5 | ภารกิจท้าทายสัปดาห์ 8 (เหมือนเดิม) |
| ห้อง 9 | 5 | แล็บท้ายคาบสัปดาห์ 12 (ชุดเดียวกันอยู่แล้ว) |
| ห้อง 10 | 6 | แล็บท้ายคาบสัปดาห์ 14 |
| ห้อง 11 | 5 | แล็บท้ายคาบสัปดาห์ 16 |

- **รูปแบบไม่เปลี่ยน:** ภารกิจ VM ทุกข้อยังเป็นข้อเดิม ใช้ปุ่มเปิด VM และคำสั่ง "เตรียมโจทย์" เดิม และตรวจคำตอบที่ได้จาก VM เหมือนเดิม ไม่มีข้อใดเปลี่ยนเป็นปรนัย
- **ไม่ต้องทำซ้ำ:** คนที่เคยทำภารกิจ VM ในห้องฝึก ได้เครดิตในแล็บสัปดาห์นั้นโดยไม่ต้องทำซ้ำ
- **แจ้งในห้องเดิม:** ภารกิจท้าทายห้อง 9–12 แสดงข้อความบอกว่า VM อยู่ที่แล็บสัปดาห์ใด พร้อมลิงก์

## 5. คะแนนและฐานข้อมูล

### หลักการ

- คีย์ข้อ (`r9-0`, `w8-0`, …), ลำดับข้อ และรหัสห้องไม่เปลี่ยน แถวคะแนนเดิมทุกแถวยังอยู่
- ข้อที่ถูกซ่อนยังอยู่ในระบบเพื่อเก็บประวัติ แต่ไม่รับคำตอบใหม่ เซิร์ฟเวอร์ตอบ 410 พร้อมบอกว่ารวมไว้ที่แล็บสัปดาห์ใด

### Migration แบบครั้งเดียว (`server/merge-rooms.js`)

ทำงานอัตโนมัติตอนเซิร์ฟเวอร์เริ่ม ขั้นตอนมีดังนี้

1. ล็อกด้วย advisory lock และทำทั้งหมดใน transaction เดียว
2. ถ้าเคยทำแล้ว (มีแถวใน `app_migrations`) จะข้ามทันที จึงไม่ทำซ้ำแม้รีสตาร์ต
3. สำรอง `task_progress` ทั้งตารางไว้ใน `backup_29_task_progress`
4. ให้เครดิตกับข้อที่เก็บไว้ สำหรับนักเรียนที่เคยตอบถูกข้อที่ถูกซ่อนหรือภารกิจ VM ในห้องฝึก:
   - เพิ่มแถวในข้อที่เก็บไว้ โดยใช้คะแนน เวลาที่ทำ จำนวนครั้งที่ตอบผิด และการใช้คำใบ้เดิม
   - ใส่ `linked_from` เป็นคีย์ต้นทาง
   - ถ้าข้อที่เก็บไว้ตอบถูกอยู่แล้ว จะไม่แตะ จึงไม่ให้คะแนนซ้ำ
   - ถ้าเคยตอบผิดในข้อที่เก็บไว้แต่ตอบถูกในห้องฝึก จะใช้ผลที่ตอบถูก
5. บันทึกสรุปผลใน `app_migrations`

### ป้องกันการนับซ้ำ

- XP, วันที่เข้าเรียนต่อเนื่อง (streak) และภารกิจประจำสัปดาห์ ไม่นับแถวที่มี `linked_from` เพราะนับไปแล้วที่แถวต้นทาง XP รวมจึงเท่าเดิม (ทดสอบแล้ว)
- คะแนนแล็บในตารางครูและหน้าผลการเรียน นับเฉพาะข้อที่ยังอยู่ในแล็บนั้น
  - ห้อง 9 จึงเต็ม 40 คะแนน (4 ข้อ)
  - คนที่เคยตอบทั้งข้อในห้องฝึกและข้อในแล็บ จะเห็นคะแนนข้อนั้นครั้งเดียว ที่แล็บ
- ครูรีเซ็ตแล็บ จะลบเฉพาะข้อที่ยังอยู่ในแล็บนั้น แถวประวัติของข้อที่ถูกซ่อนยังอยู่
- ถ้าครูรีเซ็ตแล็บสัปดาห์แล้วนักเรียนตอบข้อที่เคยได้เครดิตอีกครั้ง แถวใหม่จะถูกตั้ง `linked_from` เพราะ XP ของข้อนั้นนับไปแล้วที่ข้อในห้องฝึก จึงไม่ได้ XP ซ้ำ
- นำเข้างานของผู้เยี่ยมชม: คำตอบของข้อที่ถูกซ่อนจะตรวจใหม่และบันทึกที่ข้อที่เก็บไว้
- นำเข้างานของผู้เยี่ยมชม:
  - คำตอบของข้อที่ถูกซ่อนตรวจกับฉบับที่ผู้เยี่ยมชมตอบจริง ลำดับตัวเลือกจึงถูกต้อง
  - บันทึกไว้เป็นประวัติของห้องนั้น และให้เครดิตแบบ linked ที่ข้อในแล็บสัปดาห์
  - ไม่สร้างหรือปิดรอบจับเวลาของแล็บสัปดาห์ นักเรียนจึงยังทำข้อที่เหลือได้
- ผู้เยี่ยมชม (คะแนนในเบราว์เซอร์) ได้เครดิตแบบเดียวกันในเครื่องตัวเอง
- **ระหว่าง deploy:** ถ้าเซิร์ฟเวอร์ 2.8 ตัวเก่ายังรับคำตอบในห้องฝึกหลัง migration ทำงานแล้ว ทุกครั้งที่เซิร์ฟเวอร์เริ่มจะให้เครดิตคำตอบที่บันทึก*หลัง*เวลา migration เพิ่ม แถวที่เก่ากว่านั้นไม่ถูกแตะอีก การรีเซ็ตของครูจึงไม่ถูกย้อนกลับ
- **เบราว์เซอร์ที่ยังใช้สคริปต์ 2.8 จากแคชในการเปิดครั้งแรกหลัง deploy:**
  - ได้ข้อมูลโจทย์รูปแบบเดิมจาก `/api/content` (ลำดับข้อเดิมครบ) คำตอบจึงไม่ไปลงผิดข้อ
  - ข้อที่ถูกซ่อนจะได้ข้อความว่าย้ายไปแล็บสัปดาห์ใด
  - สคริปต์ 2.9 ขอข้อมูลแบบใหม่ด้วย `/api/content?v=29`

### ผลกระทบที่ควรรู้

- **คะแนนรวมแล็บในตารางครูอาจลดลงสำหรับนักเรียนบางคน** เฉพาะคนที่ตอบข้อซ้ำถูกทั้งสองที่ เพราะข้อซ้ำนับครั้งเดียวแล้ว XP ไม่ลด
- **คะแนนเต็มของห้อง 2, 4, 6, 9, 10, 12 ลดลง** ตามจำนวนข้อที่ซ่อน คนที่เคยทำครบยังได้เต็ม
- **เวลา (`solved_at`) ของแถวเครดิต** เป็นเวลาที่ตอบในห้องฝึก แถวเครดิตไม่สร้างรอบจับเวลา (`lab_runs`) ของแล็บสัปดาห์ นักเรียนยังต้องกด Start เพื่อทำข้อที่เหลือ

### Backup และ Rollback

**ก่อน deploy:** สำรองข้อมูลจากแดชบอร์ดผู้ดูแล (`/api/admin/backup`) หรือ `pg_dump` จาก Railway

**คำสั่ง** (ตั้ง `DATABASE_URL` ก่อน):

```bash
DATABASE_URL=... node scripts/merge-rooms.js --plan       # ดูว่าจะให้เครดิตกี่แถว กี่คน (ไม่เขียนข้อมูล)
DATABASE_URL=... node scripts/merge-rooms.js --status     # ดูว่าทำไปแล้วหรือยัง และทำอะไรไป
DATABASE_URL=... node scripts/merge-rooms.js --rollback   # ลบแถวที่เพิ่ม และคืนค่าแถวที่แก้จาก backup_29_task_progress
```

**ลำดับการย้อนกลับ:**
1. ตั้ง `NETLAB_SKIP_MERGE=1` บน Railway
2. deploy โค้ด 2.8 กลับ (ข้อมูลเนื้อหาต้องกลับเป็นแบบเดิมด้วย ถ้าคงโค้ด 2.9 ไว้ ข้อที่ถูกซ่อนยังรับคำตอบไม่ได้ เครดิตจะหายไป)
3. รัน `--rollback` จากโฟลเดอร์ 2.9 กับฐานข้อมูลเดียวกัน (คอลัมน์ `linked_from` ที่เหลืออยู่ไม่กระทบ 2.8)

**ตาราง backup:** ยังไม่ลบ ให้ลบเองหลังมั่นใจแล้ว ด้วย `DROP TABLE backup_29_task_progress`

**ทดสอบกับข้อมูลจำลองแล้ว** (`tests/merge-rooms.test.js` และ e2e part10):
- dry run ไม่เขียนข้อมูล
- ให้เครดิตถูกต้อง ไม่นับซ้ำ และ XP เท่าเดิม
- รันซ้ำและรีสตาร์ตแล้วไม่ทำซ้ำ
- catch-up ระหว่าง deploy ไม่ย้อนการรีเซ็ตของครู
- ตอบใหม่หลังรีเซ็ตไม่ได้ XP ซ้ำ
- นำเข้างานผู้เยี่ยมชมไม่ปิดแล็บสัปดาห์
- rollback แล้วตารางกลับเหมือนก่อน migration ทุกแถว
